# 自動リプライの監視と復旧

## リリース順序

1. `20260910000000_auto_reply_claim.sql` をDBへ適用する（既存データの削除・変更なし）。
2. 新しいアプリをデプロイする。旧版の実行が残る間は新旧の同時実行を避ける。
3. cron-job.org の `/api/cron/auto-reply` の実行履歴・失敗通知設定を確認する。
   エンドポイントを手動実行すると条件を満たす投稿へ実際に返信する。

この変更はスケジュールの登録や通知先の設定自体は行わない。

## 応答とログ

`replied` はThreadsから投稿成功の応答を受けた件数、`checked` は時間内の判定対象数。
`failed` と `errors` を追加し、1件でも失敗があればHTTP 500を返す。他の投稿は処理を続ける。
成功時はHTTP 200。`[auto-reply] completed` に実行集計、`[auto-reply] failure` に失敗を出力する。

`errors` は `postId`、`stage`、取得済みなら `replyId` を含む。
秘密値を含み得るAPIレスポンス・例外本文・トークン・返信文面は出力しない。
そのため外部APIの詳細なエラー本文はこのログからは確認できない。

| stage | 確認するもの |
| --- | --- |
| load_posts | DB接続、マイグレーション適用、Supabaseの稼働状況 |
| config | アカウントのトークン・ユーザーID・文面・発火条件の欠損 |
| decrypt | 暗号鍵と保存トークンの整合性 |
| metrics | Threadsの権限・トークン期限・対象投稿の存在 |
| claim | DBへの更新可否 |
| publish | Threadsに実際の返信が存在するか |
| persist | replyIdの実在確認とDBへの成功記録の修復 |
| reconcile | 15分以上未解決の送信試行。実際の返信を確認して復旧 |

## 二重送信を避けるための停止と復旧

送信前に `cta_reply_claimed_at IS NULL` を条件にDBを更新し、1つの実行だけが処理権を得る。
更新失敗または更新件数0なら送信しない。同じDB行への同時実行・再実行を防ぐ。
同じThreads投稿が別のDB行に重複登録されている場合の重複排除は対象外。

送信タイムアウト・送信失敗・成功記録の保存失敗・プロセス中断でも処理権は自動解除しない。
外部サービスへの送信とDB更新は単一トランザクションにできないため、結果不明時は再送より確認を優先する。
メトリクス取得など送信前の失敗は処理権を取得していないので次回再試行できる。

未解決の処理権は15分後から `reconcile` として報告し、発火時間を過ぎても報告する。
復旧時は該当投稿への実際の返信と実行ログを照合し、稼働中の処理がないことを確認する。

- 返信が存在する場合：`cta_reply_posted=true`、`cta_reply_post_id=実在する返信ID` を保存する。
- 返信が存在しないと確認できた場合のみ：`cta_reply_claimed_at=NULL` に戻す。
  発火時間内なら次回判定で再送対象になり得る。時間外なら再送されない。
- 判別できない場合：処理権を残して調査を継続する。

自動期限切れによる解除や、未解決行の一括解除は行わない。

## 取得件数

ID順のカーソルで空ページまで読み進め、DBの1回の取得上限による取りこぼしを防ぐ。
処理中に成功行が未返信集合から外れても、offset方式と異なり次の行を飛ばさない。
外部APIへの同時処理は5件まで。古い未返信行の走査コストは残るため、規模拡大時には
アカウント別の時間条件によるDB側の絞り込みや実行分割を検討する。
